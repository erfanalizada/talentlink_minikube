1. Introduction to Observability

Observability is the ability to understand the internal state of a system by examining its external outputs. In modern microservices architectures like TalentLink, observability is critical for debugging, performance optimization, and maintaining system health.

Why Observability Matters

With CQRS implementation in our User and Job services, we need visibility into:

  • How long commands and queries take to execute
  • Which endpoints are being called most frequently
  • How requests flow through the system (commands → handlers → services → database)
  • Where bottlenecks and errors occur in the request lifecycle

TalentLink implements a complete observability stack using three industry-standard tools: Prometheus for metrics collection, Grafana for visualization, and Jaeger for distributed tracing.

2. Three Pillars of Observability

Modern observability is built on three fundamental pillars, each providing different insights into system behavior:

📊 Metrics

Tool: Prometheus

  • Numerical measurements over time
  • CPU, memory, request counts
  • Response times, error rates
  • Aggregated statistical data

📈 Visualization

Tool: Grafana

  • Dashboards and graphs
  • Real-time monitoring
  • Historical trend analysis
  • Alerting and notifications

🔍 Traces

Tool: Jaeger

  • Request flow tracking
  • Service dependencies
  • Performance bottlenecks
  • Error propagation paths

Together They Provide Complete Visibility

Metrics tell you what is happening (e.g., "requests are slow")
Traces tell you where it's happening (e.g., "database queries in the command handler")
Visualization helps you understand and act on the data

3. Prometheus - Metrics Collection

What is Prometheus?

Prometheus is an open-source monitoring and alerting toolkit designed for reliability and scalability. It collects and stores metrics as time-series data, recording information with timestamps.

Purpose in TalentLink

Key Responsibilities

  • Scrape metrics from user-service and job-service endpoints
  • Store time-series data about HTTP requests, response times, and errors
  • Monitor system health (CPU, memory, pod status)
  • Provide a query language (PromQL) for data analysis
  • Enable alerting based on metric thresholds

Metrics Collected

Metric Type Example Description
Request Count flask_http_request_total Total number of HTTP requests per endpoint
Request Duration flask_http_request_duration_seconds Time taken to process requests
Error Rate flask_http_request_exceptions_total Number of failed requests
Service Info user_service_info, job_service_info Service metadata and version

Deployment in TalentLink

k8s/monitoring/ ├── prometheus-rbac.yaml # RBAC permissions for Prometheus ├── prometheus-config.yaml # Scrape configuration ├── prometheus-deployment.yaml # Deployment & Service └── prometheus-ingress.yaml # Ingress for web UI

Access Prometheus

URL: http://prometheus.local

Prometheus automatically discovers and scrapes metrics from pods annotated with prometheus.io/scrape: "true"

4. Grafana - Metrics Visualization

What is Grafana?

Grafana is an open-source analytics and visualization platform. It transforms raw metrics from Prometheus into beautiful, interactive dashboards that help teams understand system behavior at a glance.

Purpose in TalentLink

Key Responsibilities

  • Visualize metrics from Prometheus in real-time dashboards
  • Create graphs, charts, and heatmaps of CQRS operation performance
  • Monitor trends over time (hourly, daily, weekly)
  • Set up alerts for anomalies (high error rates, slow responses)
  • Provide insights into command vs query performance

Example Dashboards

User Service Dashboard

  • CreateUserProfileCommand execution time
  • GetUserProfileByIdQuery throughput
  • Profile picture upload success rate
  • Database query latency

Job Service Dashboard

  • Job posting command performance
  • Application query response times
  • CQRS handler execution metrics
  • Service health indicators

Deployment in TalentLink

5. Jaeger - Distributed Tracing

What is Jaeger?

Jaeger is an open-source distributed tracing system. It tracks requests as they flow through multiple services and components, showing exactly where time is spent and where errors occur in complex transactions.

Purpose in TalentLink

Key Responsibilities

  • Trace CQRS command and query execution end-to-end
  • Track request flow: Route → Command/Query → Handler → Service → Repository → Database
  • Identify performance bottlenecks in the execution chain
  • Show SQLAlchemy query execution timing
  • Visualize service dependencies and call graphs

What Gets Traced?

Component Traced Operations Insights Gained
Flask Requests All HTTP endpoints Total request duration, endpoint performance
CQRS Handlers Command/Query execution Handler processing time, business logic overhead
Service Layer Business logic operations Service method performance
Database SQLAlchemy queries Query execution time, connection overhead

7. Code Implementation

Dependencies Added

Both user-service and job-service have been instrumented with monitoring libraries:

# Prometheus metrics
prometheus-flask-exporter==0.23.0

# OpenTelemetry for distributed tracing
opentelemetry-api==1.21.0
opentelemetry-sdk==1.21.0
opentelemetry-instrumentation-flask==0.42b0
opentelemetry-instrumentation-sqlalchemy==0.42b0
opentelemetry-exporter-jaeger==1.21.0

User Service Implementation

File: backend/user-service/app.py

from prometheus_flask_exporter import PrometheusMetrics
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.jaeger.thrift import JaegerExporter
from opentelemetry.instrumentation.flask import FlaskInstrumentor
from opentelemetry.instrumentation.sqlalchemy import SQLAlchemyInstrumentor

def create_app():
    app = Flask(__name__)

    # Initialize Prometheus metrics
    metrics = PrometheusMetrics(app)
    metrics.info('user_service_info', 'User Service with CQRS', version='1.0.0')

    # Initialize Jaeger tracing
    jaeger_host = os.getenv('JAEGER_HOST', 'jaeger')
    jaeger_port = int(os.getenv('JAEGER_PORT', '6831'))

    resource = Resource.create({"service.name": "user-service"})
    trace.set_tracer_provider(TracerProvider(resource=resource))

    jaeger_exporter = JaegerExporter(
        agent_host_name=jaeger_host,
        agent_port=jaeger_port,
    )

    trace.get_tracer_provider().add_span_processor(
        BatchSpanProcessor(jaeger_exporter)
    )

    # Instrument Flask app for automatic tracing
    FlaskInstrumentor().instrument_app(app)

    # Register blueprints
    app.register_blueprint(user_bp)

    # Initialize database and instrument SQLAlchemy
    with app.app_context():
        init_db()
        SQLAlchemyInstrumentor().instrument()

    return app

What This Code Does

  • PrometheusMetrics(app): Automatically instruments all Flask routes to expose metrics at /metrics
  • FlaskInstrumentor: Creates distributed traces for all HTTP requests
  • SQLAlchemyInstrumentor: Traces all database queries with execution time
  • JaegerExporter: Sends trace data to Jaeger collector

Kubernetes Deployment Configuration

Pod Annotations for Prometheus

apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  template:
    metadata:
      annotations:
        prometheus.io/scrape: "true"     # Enable scraping
        prometheus.io/port: "5000"       # Metrics port
        prometheus.io/path: "/metrics"  # Metrics endpoint
    spec:
      containers:
      - name: user-service
        env:
        - name: JAEGER_HOST
          value: "jaeger"
        - name: JAEGER_PORT
          value: "6831"

Automatic Instrumentation Benefits

With this configuration, no manual code changes are needed in CQRS handlers, services, or repositories. OpenTelemetry automatically:

  • Traces every HTTP request through the entire CQRS flow
  • Records SQL queries executed by repositories
  • Measures execution time at each layer
  • Propagates trace context across service boundaries

9. How to Use the Monitoring Stack

Step 1: Generate Traffic

Visit your application and perform operations:

  • Create user profiles (POST commands)
  • View profiles (GET queries)
  • Upload profile pictures
  • Create and view job postings

Step 2: View Metrics in Prometheus

Access: http://prometheus.local

Example Queries:

  • up - Check which services are running
  • flask_http_request_total - Total requests per service
  • rate(flask_http_request_duration_seconds_sum[5m]) - Average response time
  • flask_http_request_exceptions_total - Error count

Step 3: Create Dashboards in Grafana

Access: http://grafana.local (admin/admin)

Create Dashboard Steps:

  1. Click "+" → "Dashboard" → "Add new panel"
  2. Select "Prometheus" as data source
  3. Enter PromQL query (e.g., flask_http_request_total)
  4. Choose visualization (Graph, Stat, Gauge, etc.)
  5. Save dashboard

Or import pre-built Flask dashboards from Grafana.com

Step 4: Trace Requests in Jaeger

Access: http://jaeger.local

How to Find Traces:

  1. Select service: "user-service" or "job-service"
  2. Click "Find Traces"
  3. Click on a trace to see detailed breakdown
  4. Examine each span to see timing
  5. Identify slow database queries or handler operations

Example: Debugging Slow Requests

Scenario: Users report slow profile creation

  1. Grafana: Confirm average response time is high (>500ms)
  2. Prometheus: Check which endpoint is affected (/api/users/profile)
  3. Jaeger: Open a trace for CreateUserProfileCommand
  4. Jaeger: See that database INSERT takes 400ms
  5. Action: Add database index or optimize query
  6. Verify: Watch metrics improve in Grafana

10. Benefits & Best Practices

Benefits of Observability in CQRS

1. Performance Optimization

Identify bottlenecks in command and query handlers, optimize database queries, and improve overall system throughput.

2. Debugging & Troubleshooting

Quickly identify where errors occur in the CQRS flow, understand failure propagation, and reduce mean time to resolution (MTTR).

3. Capacity Planning

Understand load patterns, predict when to scale services, and optimize resource allocation for commands vs queries.

4. CQRS-Specific Insights

Compare write (command) vs read (query) performance, identify command/query ratio, and optimize each path independently.

5. Business Intelligence

Track feature usage (which commands/queries are most popular), understand user behavior patterns, and make data-driven product decisions.

Best Practices

DO's

  • Monitor both commands and queries separately
  • Set up alerts for high error rates or slow responses
  • Create dashboards for each CQRS service
  • Use traces to understand complex workflows
  • Regularly review metrics for optimization opportunities
  • Document baselines for normal system behavior

DON'Ts

  • ✗ Don't rely on metrics alone - use logs and traces together
  • ✗ Don't ignore slow queries - they compound under load
  • ✗ Don't over-instrument - too many metrics create noise
  • ✗ Don't forget to set retention policies for metrics/traces
