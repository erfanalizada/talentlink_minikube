🔌 1. Connection Pooling

IMPLEMENTED PRODUCTION-READY

Overview

SQLAlchemy connection pooling has been configured to efficiently manage database connections and prevent connection exhaustion under high load.

Configuration

Parameter Value Description
pool_size 20 Number of persistent connections to keep open
max_overflow 10 Additional connections when pool is exhausted
pool_timeout 30 seconds Maximum wait time for a connection
pool_recycle 3600 seconds Recycle connections every hour to prevent stale connections
pool_pre_ping True Verify connections are alive before using them

Modified Files

backend/job-service/database.py (lines 18-26)
backend/user-service/database.py (lines 23-31)

Code Implementation

engine = create_engine(
    DATABASE_URL,
    echo=True,
    pool_size=20,          # Number of connections to keep open
    max_overflow=10,       # Additional connections when pool is exhausted
    pool_timeout=30,       # Seconds to wait for a connection
    pool_recycle=3600,     # Recycle connections after 1 hour
    pool_pre_ping=True     # Verify connections before using them
)

Benefits

  • Reduces database connection overhead
  • Prevents connection exhaustion during traffic spikes
  • Automatically recovers from stale connections
  • Supports up to 30 concurrent connections per service (20 + 10 overflow)
💡 Tip: Monitor connection pool metrics using prometheus-flask-exporter to optimize pool_size for your workload.

⚡ 3. Horizontal Pod Autoscaler (HPA)

IMPLEMENTED REQUIRES METRICS SERVER

Overview

Kubernetes HPA automatically scales services based on CPU and memory utilization, ensuring optimal performance during traffic spikes and cost efficiency during low traffic.

Scaling Configuration

Parameter Value Description
Min Replicas 1 Always maintain at least 1 pod
Max Replicas 5 Scale up to 5 pods under load
CPU Threshold 70% Scale when CPU exceeds 70% utilization
Memory Threshold 80% Scale when memory exceeds 80% utilization
Scale-Up Time Immediate Fast response to traffic spikes
Scale-Down Time 5 minutes Gradual scale-down prevents flapping

New Files Created

k8s/backend/job/hpa.yaml
k8s/backend/user/hpa.yaml
k8s/backend/auth/hpa.yaml

Code Example

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: job-service-hpa
  namespace: talentlink-local
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: job-service
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

Scaling Behavior

  • Scale-Up Policy: Add up to 2 pods or double capacity every 15 seconds (whichever is greater)
  • Scale-Down Policy: Remove up to 50% of pods every 15 seconds after 5-minute stabilization
  • Metrics Evaluation: Every 15 seconds
  • Decision Making: Takes the maximum of CPU and memory metrics
⚠️ Prerequisites: Metrics Server must be installed in your Kubernetes cluster for HPA to function. In Minikube, enable it with: minikube addons enable metrics-server

💾 4. Redis Caching Layer

IMPLEMENTED PERSISTENT STORAGE

Overview

Redis has been deployed as a centralized caching layer to reduce database load and improve response times for frequently accessed data.

Redis Configuration

Setting Value Purpose
Image redis:7-alpine Lightweight, latest stable version
Persistence AOF (Append-Only File) Durability with minimal performance impact
Max Memory 256 MB Memory limit for cache entries
Eviction Policy allkeys-lru Least Recently Used eviction when full
Storage 2Gi PVC Persistent volume for AOF file
Resources 100m-500m CPU
128Mi-512Mi RAM		 Guaranteed resources

New Files Created

k8s/backend/redis/deployment.yaml
backend/job-service/cache.py

Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: redis
  namespace: talentlink-local
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: redis
          image: redis:7-alpine
          command:
            - redis-server
            - --appendonly
            - "yes"
            - --maxmemory
            - "256mb"
            - --maxmemory-policy
            - allkeys-lru

Health Checks

  • Liveness Probe: TCP socket check on port 6379 every 10 seconds
  • Readiness Probe: redis-cli ping command every 5 seconds
  • Initial Delay: 30 seconds for startup

Cache Framework Features

  • Decorator-based caching: Simple @cache_query decorator for functions
  • Automatic serialization: Handles SQLAlchemy models, lists, and dicts
  • Configurable TTL: Set different cache durations per query
  • Graceful degradation: Falls back to direct database queries if Redis is unavailable
  • Pattern-based invalidation: Invalidate multiple related cache entries at once
  • Connection pooling: Reuses Redis connections efficiently

🔄 5. CQRS Query Caching

IMPLEMENTED AUTO-INVALIDATION

Overview

The CQRS pattern has been enhanced with intelligent caching for read operations and automatic cache invalidation for write operations.

Cached Queries

Query Cache Key Pattern TTL Use Case
GetAllJobsQuery jobs:all 5 minutes Job listing page (high traffic)
GetJobByIdQuery jobs:by_id:{job_id} 10 minutes Job detail page (rarely changes)
GetJobsByEmployerQuery jobs:by_employer:{employer_id} 5 minutes Employer dashboard
GetAllJobsWithApplicationStatusQuery jobs:with_status:{employee_id} 3 minutes Employee job browsing (personalized)

Cache Invalidation Strategy

Command Invalidated Cache Patterns Reason
CreateJobCommand jobs:all:*
jobs:by_employer:*{employer_id}*		 New job affects all jobs list and employer's jobs
UpdateJobCommand jobs:* Job details changed, invalidate all job caches
DeleteJobCommand jobs:* Job removed, invalidate all job caches
ApplyToJobCommand jobs:with_status:*{employee_id}* Application status changed for employee

Modified Files

backend/job-service/cqrs/handlers/query_handlers.py
backend/job-service/cqrs/handlers/command_handlers.py
backend/job-service/requirements.txt
k8s/backend/job/deployment.yaml (added Redis env vars)

Code Example - Query Caching

from cache import cache_query

class JobQueryHandler:
    @cache_query("jobs:all", ttl=300)
    def handle_get_all_jobs(self, query: GetAllJobsQuery) -> List[Job]:
        """
        Handle GetAllJobsQuery.
        Returns all job postings.
        Cached for 5 minutes.
        """
        return self.service.get_all_jobs()

Code Example - Cache Invalidation

from cache import invalidate_cache

class JobCommandHandler:
    def handle_create_job(self, command: CreateJobCommand) -> Job:
        job = self.service.create_job(...)

        # Invalidate relevant caches
        invalidate_cache("jobs:all:*")
        invalidate_cache(f"jobs:by_employer:*{command.employer_id}*")

        return job

Environment Variables

Variable Default Description
REDIS_HOST redis Redis service hostname
REDIS_PORT 6379 Redis service port
REDIS_ENABLED true Enable/disable caching globally
REDIS_DEFAULT_TTL 300 Default cache TTL in seconds (5 minutes)
✅ Smart Caching: The framework automatically handles cache hits/misses and logs them for monitoring. Cache failures gracefully degrade to direct database queries.

🚀 6. Deployment Instructions

Step 1: Deploy Redis

# Deploy Redis with persistence
kubectl apply -f k8s/backend/redis/deployment.yaml

# Verify Redis is running
kubectl get pods -n talentlink-local | grep redis
kubectl logs -n talentlink-local deployment/redis

Step 2: Enable Metrics Server (for HPA)

# For Minikube
minikube addons enable metrics-server

# For other Kubernetes clusters, install metrics-server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Verify metrics server
kubectl top nodes
kubectl top pods -n talentlink-local

Step 3: Apply HPA Configurations

# Deploy HPA for all services
kubectl apply -f k8s/backend/job/hpa.yaml
kubectl apply -f k8s/backend/user/hpa.yaml
kubectl apply -f k8s/backend/auth/hpa.yaml

# Verify HPA is active
kubectl get hpa -n talentlink-local

Step 4: Update Service Deployments

# Apply updated deployments with resource limits
kubectl apply -f k8s/backend/job/deployment.yaml
kubectl apply -f k8s/backend/user/deployment.yaml
kubectl apply -f k8s/backend/auth/deployment.yaml
kubectl apply -f k8s/backend/cv/deployment.yaml
kubectl apply -f k8s/backend/matching/deployment.yaml
kubectl apply -f k8s/backend/notification/deployment.yaml

# Watch pods restart with new configuration
kubectl get pods -n talentlink-local -w

Step 5: Rebuild Services with New Dependencies

# Job service needs redis dependency and cache.py
cd backend/job-service
docker build -t ghcr.io/erfanalizada/talentlink_minikube-job-service:latest .
docker push ghcr.io/erfanalizada/talentlink_minikube-job-service:latest

# User service needs connection pooling updates
cd backend/user-service
docker build -t ghcr.io/erfanalizada/talentlink_minikube-user-service:latest .
docker push ghcr.io/erfanalizada/talentlink_minikube-user-service:latest

# Restart deployments to pull new images
kubectl rollout restart deployment/job-service -n talentlink-local
kubectl rollout restart deployment/user-service -n talentlink-local

Step 6: Verify Deployment

# Check all pods are running
kubectl get pods -n talentlink-local

# Check HPA status
kubectl get hpa -n talentlink-local

# Check service logs for cache activity
kubectl logs -n talentlink-local deployment/job-service | grep Cache

# Test Redis connectivity
kubectl exec -it deployment/redis -n talentlink-local -- redis-cli ping
⚠️ Important: Make sure to push updated Docker images to your container registry before applying Kubernetes deployments.

Prometheus Queries

🔮 9. Future Enhancements

Short-term (1-3 months)

  • Database Read Replicas: Separate read and write database instances for better load distribution
  • Redis Clustering: High availability Redis setup with Sentinel or Redis Cluster
  • Custom Metrics for HPA: Scale based on request queue depth, cache hit ratio, or custom business metrics
  • Cache Warming: Pre-populate cache with frequently accessed data on startup
  • Distributed Tracing: Enhanced Jaeger integration for cache performance analysis

Medium-term (3-6 months)

  • ElasticSearch Integration: Full-text search for job listings with caching
  • CDN Integration: Cache static assets and API responses at edge locations
  • Database Sharding: Partition large tables across multiple database instances
  • GraphQL Layer: Implement GraphQL with DataLoader for N+1 query optimization
  • Service Mesh: Istio or Linkerd for advanced traffic management

Long-term (6-12 months)

  • Multi-Region Deployment: Geo-distributed databases with regional caching
  • Event Streaming: Kafka for real-time cache invalidation across regions
  • Machine Learning Cache Optimization: Predict cache eviction and warming needs
  • Serverless Functions: AWS Lambda/Cloud Functions for burst workloads
  • Time-Series Database: InfluxDB for metrics and analytics workloads

Architectural Patterns to Consider

Pattern Use Case Complexity Impact
Read Replicas Separate read/write workloads Medium High - reduces master DB load
Write-Through Cache Always consistent cache Low Medium - better consistency
Materialized Views Complex aggregations Medium High - pre-computed results
Database Partitioning Very large tables (>100M rows) High Very High - horizontal scaling
Event Sourcing Extension Rebuild read models from events High Very High - full auditability
💡 Recommendation: Monitor current metrics for 2-4 weeks before implementing additional enhancements. Focus on optimizations that address actual bottlenecks rather than theoretical improvements.
