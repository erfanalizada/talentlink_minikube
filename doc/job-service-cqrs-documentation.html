1. Introduction to CQRS

CQRS (Command Query Responsibility Segregation) is a design pattern that separates read and write operations for a data store. Instead of using a single model for both reading and writing data, CQRS uses different models: Commands for writes and Queries for reads.

Core Principle

Commands: Change the state of the system (Create, Update, Delete)
Queries: Return data without modifying state (Read operations)

Commands (Write)

  • Modify system state
  • Perform validation
  • Execute business logic
  • Return success/failure

Queries (Read)

  • Never modify state
  • Return data
  • Can be cached
  • Optimized for reading

2. CQRS in Job Service

The Job Service implements CQRS to manage both job postings and job applications. The implementation is organized into two main domains: Jobs and Applications, each with their own commands and queries.

Job Operations

Operation Type HTTP Method CQRS Type Example
Create Job POST Command CreateJobCommand
Get All Jobs GET Query GetAllJobsQuery
Get Job by ID GET Query GetJobByIdQuery
Get Jobs by Employer GET Query GetJobsByEmployerQuery
Update Job PUT/PATCH Command UpdateJobCommand
Delete Job DELETE Command DeleteJobCommand

Application Operations

Operation Type HTTP Method CQRS Type Example
Apply to Job POST Command ApplyToJobCommand
Get Applications by Job GET Query GetApplicationsByJobQuery
Get Applications by Employee GET Query GetApplicationsByEmployeeQuery
Update Application Status PUT/PATCH Command UpdateApplicationStatusCommand
Delete Application DELETE Command DeleteApplicationCommand

3. Folder Structure

The CQRS implementation is organized in a clean, modular structure within the backend/job-service/cqrs/ directory:

backend/job-service/cqrs/ ├── __init__.py # Main exports for CQRS module ├── commands/ │ ├── __init__.py # Command exports │ ├── job_commands.py # Job command definitions │ └── application_commands.py # Application command definitions ├── queries/ │ ├── __init__.py # Query exports │ ├── job_queries.py # Job query definitions │ └── application_queries.py # Application query definitions └── handlers/ ├── __init__.py # Handler exports ├── command_handlers.py # Command execution logic └── query_handlers.py # Query execution logic
Important: The Job service handles two distinct domains (Jobs and Applications), each with their own commands and queries. However, handlers are unified in single files for simplicity.

4. Commands - Write Operations

Responsibility

Job Command Definitions

from typing import Optional, List

Job-related command definitions.

    skills: Optional[List[str]] = None

class DeleteJobCommand:
    """Command to delete a job posting."""
    job_id: int
    employer_id: str

6. Handlers - Execution Layer

File: cqrs/handlers/command_handlers.py

Responsibility

  • Execute job and application commands
  • Delegate to appropriate service layer
  • Coordinate business logic execution
  • Handle authorization and validation
from typing import Optional
from services import JobService, JobApplicationService
from models import Job, JobApplication


class JobCommandHandler:
    """Handler for job-related commands."""

    def __init__(self, service: JobService):
        self.service = service

    def handle_create_job(self, command: CreateJobCommand) -> Job:
        """Handle CreateJobCommand."""
        return self.service.create_job(
            employer_id=command.employer_id,
            title=command.title,
            description=command.description,
            salary=command.salary,
            skills=command.skills
        )

    def handle_update_job(self, command: UpdateJobCommand) -> Optional[Job]:
        """Handle UpdateJobCommand."""
        return self.service.update_job(
            job_id=command.job_id,
            employer_id=command.employer_id,
            title=command.title,
            description=command.description,
            salary=command.salary,
            skills=command.skills
        )

    def handle_delete_job(self, command: DeleteJobCommand) -> bool:
        """Handle DeleteJobCommand."""
        return self.service.delete_job(
            job_id=command.job_id,
            employer_id=command.employer_id
        )


class ApplicationCommandHandler:
    """Handler for application-related commands."""

    def __init__(self, service: JobApplicationService):
        self.service = service

    def handle_apply_to_job(self, command: ApplyToJobCommand) -> JobApplication:
        """Handle ApplyToJobCommand."""
        return self.service.create_application(
            job_id=command.job_id,
            employee_id=command.employee_id,
            cv_base64=command.cv_base64,
            portfolio_url=command.portfolio_url,
            cv_url=command.cv_url
        )

    def handle_update_application_status(self, command: UpdateApplicationStatusCommand) -> Optional[JobApplication]:
        """Handle UpdateApplicationStatusCommand."""
        return self.service.update_application_status(
            application_id=command.application_id,
            employer_id=command.employer_id,
            status=command.status
        )

    def handle_delete_application(self, command: DeleteApplicationCommand) -> bool:
        """Handle DeleteApplicationCommand."""
        return self.service.delete_application(
            application_id=command.application_id,
            employer_id=command.employer_id
        )

from typing import List, Optional, Dict
from services import JobService, JobApplicationService
from models import Job, JobApplication


class JobQueryHandler:
    """Handler for job-related queries."""

    def __init__(self, service: JobService):
        self.service = service

    def handle_get_all_jobs(self, query: GetAllJobsQuery) -> List[Job]:
        """Handle GetAllJobsQuery."""

    def handle_get_job_by_id(self, query: GetJobByIdQuery) -> Optional[Job]:
        """Handle GetJobByIdQuery."""
        return self.service.get_job(query.job_id)

    def handle_get_jobs_by_employer(self, query: GetJobsByEmployerQuery) -> List[Job]:
        """Handle GetJobsByEmployerQuery."""
        return self.service.get_jobs_by_employer(query.employer_id)

    def handle_get_all_jobs_with_application_status(self, query: GetAllJobsWithApplicationStatusQuery) -> List[Dict]:
        """Handle GetAllJobsWithApplicationStatusQuery."""

7. Integration with Routes

The routes layer integrates CQRS by creating command/query objects from HTTP requests and executing them through handlers.

Factory Functions

Responsibility of Factory Functions

  • Create database session
  • Instantiate repositories with session
  • Instantiate services with repositories
  • Create command and query handlers with services
  • Return handlers and session for cleanup
def get_job_handlers():
    """Factory function for job CQRS handlers."""
    db = SessionLocal()
    repository = JobRepository(db)
    service = JobService(repository)
    command_handler = JobCommandHandler(service)
    query_handler = JobQueryHandler(service)
    return command_handler, query_handler, db


def get_application_handlers():
    """Factory function for application CQRS handlers."""
    db = SessionLocal()
    job_repository = JobRepository(db)
    app_repository = JobApplicationRepository(db)
    service = JobApplicationService(app_repository, job_repository)
    command_handler = ApplicationCommandHandler(service)
    query_handler = ApplicationQueryHandler(service)
    return command_handler, query_handler, db

Example: Create Job (Command)

@jobs_bp.route("/api/jobs", methods=["POST"])
def create_job():
    """Create a new job posting (Employer only) - COMMAND."""
    data = request.get_json()

    # Step 1: Create command object
    command = CreateJobCommand(
        employer_id=data.get("employer_id"),
        title=data.get("title"),
        description=data.get("description"),
        salary=data.get("salary"),
        skills=data.get("skills", [])
    )

    # Step 2: Get handlers
    command_handler, _, db = get_job_handlers()

    try:
        # Step 3: Execute command
        job = command_handler.handle_create_job(command)
        return jsonify(job.to_dict()), 201
    finally:
        db.close()

Example: Get All Jobs (Query)

@jobs_bp.route("/api/jobs", methods=["GET"])
def get_all_jobs():
    """Get all job postings (Public) - QUERY."""
    employee_id = request.args.get("employee_id")

    _, query_handler, db = get_job_handlers()

    try:
        if employee_id:
            # Query with application status for employee
            query = GetAllJobsWithApplicationStatusQuery(employee_id=employee_id)
            jobs_with_status = query_handler.handle_get_all_jobs_with_application_status(query)
            return jsonify(jobs_with_status), 200
        else:
            # Query all jobs
            query = GetAllJobsQuery()
            jobs = query_handler.handle_get_all_jobs(query)
            return jsonify([job.to_dict() for job in jobs]), 200
    finally:
        db.close()

Example: Apply to Job (Command)

@jobs_bp.route("/api/jobs/<int:job_id>/apply", methods=["POST"])
def apply_to_job(job_id):
    """Apply to a job (Employee only) - COMMAND."""
    data = request.get_json()

    # Create command
    command = ApplyToJobCommand(
        job_id=job_id,
        employee_id=data.get("employee_id"),
        cv_base64=data.get("cv_base64"),
        portfolio_url=data.get("portfolio_url"),
        cv_url=data.get("cv_url")
    )

    # Execute command
    command_handler, _, db = get_application_handlers()

    try:
        application = command_handler.handle_apply_to_job(command)
        return jsonify(application.to_dict()), 201
    finally:
        db.close()

8. Complete Flow Diagram

Command Flow (Write Operation)

HTTP POST/PUT/DELETE Request
↓
Route extracts data
↓
Creates Command Object
↓
Factory creates handlers
↓
Command Handler executes
↓
Service Layer processes
↓
Repository persists to DB
↓
Returns modified entity
↓
HTTP Response (201/200)

Query Flow (Read Operation)

HTTP GET Request
↓
Route extracts parameters
↓
Creates Query Object
↓
Factory creates handlers
↓
Query Handler executes
↓
Service retrieves data
↓
Returns data from DB
↓
HTTP Response (200)

9. Component Relationships

Dependency Flow

Route Layer (routes.py)
    ↓ uses
Command/Query Objects (commands/*.py, queries/*.py)
    ↓ passed to
Handlers (handlers/*.py)
    ↓ delegates to
Service Layer (services.py)
    ↓ uses
Repository Layer (repositories.py)
    ↓ accesses
Database (via SQLAlchemy)

Component Interaction Table

Component Creates/Uses Depends On Returns To
Routes Command/Query objects Handlers, Factory HTTP Client
Factory Functions Handlers, Services, Repositories Database Session Routes
Job Command Handler JobService calls JobService Routes
Application Command Handler JobApplicationService calls JobApplicationService Routes
Job Query Handler JobService calls JobService Routes
Application Query Handler JobApplicationService calls JobApplicationService Routes
Services Business logic Repository Handlers
Repositories Database queries Database Session Services

How Components Complete Each Other

Commands + Command Handlers

Job/Application Commands define what to do (the intention), while Command Handlers define how to do it (the execution). Each domain has its own handler for specialized logic.

Queries + Query Handlers

Job/Application Queries define what data to retrieve, while Query Handlers define how to retrieve it. Separate handlers allow for domain-specific optimizations.

Handlers + Service Layer

Handlers orchestrate the flow, while Services contain business logic. JobService handles job logic, JobApplicationService handles application logic including authorization.

Service + Repository

Services contain business rules, Repositories handle data persistence. The application service uses both JobRepository and JobApplicationRepository for cross-domain operations.

10. Benefits and Best Practices

Benefits of CQRS Implementation

1. Domain Separation

Jobs and Applications are clearly separated at the command/query level while sharing handler infrastructure.

2. Authorization Integration

Commands and queries include user IDs, making authorization checks straightforward and consistent.

3. Optimized Queries

Queries like GetAllJobsWithApplicationStatusQuery are optimized for specific use cases (employee job browsing).

4. Scalability

Job listings (read-heavy) and applications (write-heavy) can be scaled independently.

5. Clarity and Intent

ApplyToJobCommand vs GetApplicationsByEmployeeQuery - names clearly express user intentions.

6. Testability

Each handler can be tested independently with mock services. Commands and queries are simple to test.

Best Practices

DO's

  • Keep commands and queries as simple data structures
  • Put authorization checks in the service layer
  • Use descriptive names that express intent clearly
  • Always close database sessions in finally blocks
  • Keep handlers focused on orchestration, not logic
  • Separate factory functions for different domains
  • Include necessary IDs for authorization in commands/queries

DON'Ts

  • ✗ Don't put business logic in command/query classes
  • ✗ Don't mix job and application logic in the same handler
  • ✗ Don't bypass handlers and call services directly from routes
  • ✗ Don't skip authorization checks in commands
  • ✗ Don't create commands/queries that violate single responsibility

Job Service Specific Considerations

Authorization Pattern

Job Operations: Require employer_id to ensure only job owners can modify
Application Operations: Commands require employee_id (apply) or employer_id (status updates)
Queries: Include appropriate IDs to filter results by ownership

CV Upload Flexibility

ApplyToJobCommand supports three methods:

  • cv_base64: Direct base64 upload in request
  • cv_url: Reference to pre-uploaded file
  • portfolio_url: External portfolio link

Future Enhancements

Potential Improvements

  • Event Sourcing: Track all job and application state changes
  • Caching: Cache job listings for better performance
  • Pagination: Add pagination support to GetAllJobsQuery
  • Search: Add SearchJobsQuery with filters (location, salary, skills)
  • Notifications: Emit events when application status changes
  • Audit Trail: Track who created/modified jobs and applications
  • Async Processing: Handle CV processing asynchronously
