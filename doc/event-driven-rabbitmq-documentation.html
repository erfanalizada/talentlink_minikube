1. Introduction

This document describes the implementation of an event-driven architecture using RabbitMQ for the Talentlink job application platform. The implementation follows a hybrid communication strategy combining synchronous REST APIs for user-facing operations with asynchronous event-driven messaging for background tasks and cross-service workflows.

Implementation Completed: RabbitMQ message broker deployed with event sourcing and pub/sub pattern for two key features:
  • Application Acceptance Notifications: Async email notifications to employees
  • User Account Deletion (GDPR): Cross-service user cleanup from Keycloak and databases

Why Event-Driven Architecture?

Traditional synchronous service-to-service communication creates tight coupling and can lead to cascading failures. Event-driven architecture solves these problems by:

  • Decoupling services: Services communicate through events without knowing about each other
  • Asynchronous processing: Non-critical tasks run in background without blocking user requests
  • Scalability: Services can scale independently based on their workload
  • Resilience: Failures in one service don't cascade to others
  • Audit trail: Event sourcing provides complete history of all system changes

Use Case: Application Acceptance Notification

When an employer accepts a job application, we need to:

  1. Update the application status in the database
  2. Send an email notification to the employee
  3. Store an event for audit purposes

Instead of making the HTTP request wait for email sending (slow and blocking), we publish an event that triggers the notification asynchronously. This keeps the API fast and responsive while ensuring reliable notification delivery.

Event Sourcing Store

The event store is a dedicated database table that persists all domain events. This provides:

  • Complete audit trail: Every state change is recorded with timestamp and user info
  • Event replay: Ability to rebuild state by replaying events
  • Debugging: Full history for troubleshooting issues
  • Analytics: Source of truth for business intelligence
-- Event Store Table Schema CREATE TABLE events ( event_id INTEGER PRIMARY KEY AUTOINCREMENT, event_type VARCHAR(100) NOT NULL, aggregate_id VARCHAR(255) NOT NULL, aggregate_type VARCHAR(100) NOT NULL, event_data JSON NOT NULL, user_id VARCHAR(255), timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP, version INTEGER DEFAULT 1, INDEX idx_event_type (event_type), INDEX idx_aggregate (aggregate_id) );

4. Event Sourcing Implementation

Event Publisher (job-service)

The event_publisher.py module handles both event persistence and publishing to RabbitMQ. This ensures that events are never lost even if RabbitMQ is temporarily unavailable.

File: backend/job-service/event_publisher.py

class EventPublisher:
    """Publishes domain events to RabbitMQ and event store."""

    def publish_event(self, event_type, aggregate_id,
                       aggregate_type, event_data, user_id=None):
        """
        Publish event to both event store and RabbitMQ.

        Steps:
        1. Store event in database (event store)
        2. Publish to RabbitMQ topic exchange
        """

        # 1. Store event in event store (database)
        event = Event(
            event_type=event_type,
            aggregate_id=str(aggregate_id),
            aggregate_type=aggregate_type,
            event_data=event_data,
            user_id=user_id,
            version=1
        )
        self.db_session.add(event)
        self.db_session.commit()

        # 2. Publish event to RabbitMQ
        self._publish_to_rabbitmq(event_type, event.to_dict())

        return event

Command Handler Integration

The ApplicationCommandHandler in the CQRS layer is responsible for executing commands and publishing events.

File: backend/job-service/cqrs/handlers/command_handlers.py

class ApplicationCommandHandler:
    def handle_update_application_status(self, command):
        """Update application status and publish event if accepted."""

        # Update application status
        application = self.service.update_application_status(
            application_id=command.application_id,
            employer_id=command.employer_id,
            status=command.status
        )

        # If application was accepted, publish ApplicationAccepted event
        if application and application.status == ApplicationStatus.ACCEPTED:
            self._publish_application_accepted_event(
                application,
                command.employer_id
            )

        return application

    def _publish_application_accepted_event(self, application, employer_id):
        """Publish ApplicationAccepted event to event store and RabbitMQ."""
        publisher = EventPublisher(self.db_session)

        event_data = {
            "application_id": application.application_id,
            "job_id": application.job_id,
            "employee_id": application.employee_id,
            "employee_email": application.employee_email,
            "employee_username": application.employee_username,
            "employer_id": employer_id,
            "status": application.status.value,
            "accepted_at": application.updated_at.isoformat()
        }

        publisher.publish_event(
            event_type="ApplicationAccepted",
            aggregate_id=application.application_id,
            aggregate_type="JobApplication",
            event_data=event_data,
            user_id=employer_id
        )
Important Design Decision: Even if RabbitMQ publishing fails, the event is already saved in the event store. A separate recovery process could later republish events from the store to RabbitMQ.

Topic Exchange Pattern

We use a topic exchange instead of direct or fanout exchanges because it provides flexible routing with patterns:

  • application.accepted - Specific event type
  • application.* - All application events
  • *.accepted - All acceptance events
  • # - All events (wildcard)
Future Extensibility: New services can easily subscribe to specific event patterns without modifying existing code. For example, an analytics service could subscribe to # to receive all events.

6. Notification Service

Event Consumer

The notification service runs an event consumer in a background thread that continuously listens for ApplicationAccepted events.

File: backend/notification-service/event_consumer.py

class EventConsumer:
    """Consumes events from RabbitMQ and processes them."""

    def start_consuming(self):
        """Start consuming events from RabbitMQ."""
        self.connect()
        queue_name = self.setup_queue()

        # Set QoS - process one message at a time
        self.channel.basic_qos(prefetch_count=1)

        # Start consuming with manual acknowledgment
        self.channel.basic_consume(
            queue=queue_name,
            on_message_callback=self.on_message,
            auto_ack=False  # Manual acknowledgment for reliability
        )

        self.channel.start_consuming()

    def on_message(self, channel, method, properties, body):
        """Callback when a message is received."""
        try:
            message = json.loads(body.decode('utf-8'))

            if message.get('event_type') == 'ApplicationAccepted':
                self.process_application_accepted(message)

            # Acknowledge message after successful processing
            channel.basic_ack(delivery_tag=method.delivery_tag)

        except Exception as e:
            print(f"Error processing message: {e}")
            # Reject message and don't requeue
            channel.basic_nack(delivery_tag=method.delivery_tag, requeue=False)

def start_event_consumer():
    """Start RabbitMQ event consumer in background thread."""
    global event_consumer

    # Wait for RabbitMQ to be ready
    time.sleep(10)

    event_consumer = EventConsumer()
    event_consumer.start_consuming()  # Blocking call

if __name__ == "__main__":
    # Start event consumer in background thread
    consumer_thread = threading.Thread(
        target=start_event_consumer,
        daemon=True
    )
    consumer_thread.start()

    # Start Flask app
    app.run(host="0.0.0.0", port=5000, debug=False)

7. User Deletion Service (GDPR Compliance)

Overview

The second implemented feature is user account deletion with GDPR compliance. When a user deletes their account, the system must remove all personal data from both the user-service database and Keycloak authentication system. This is a perfect use case for event-driven architecture.

GDPR Requirement: Under GDPR (General Data Protection Regulation), users have the "right to be forgotten." When a user requests account deletion, all their personal data must be removed from all systems.

User-Service Implementation

Event Publisher Integration

The user-service uses the same EventPublisher class as job-service to store and publish events.

File: backend/user-service/cqrs/handlers/command_handlers.py

class UserCommandHandler:
    def __init__(self, service: UserProfileService, db_session=None):
        self.service = service
        self.db_session = db_session

    def handle_delete_profile(self, command):
        """Delete user profile and publish UserDeleted event."""

        # Get user profile before deletion (for event data)
        user_profile = self.service.get_profile(command.user_id)
        if not user_profile:
            return False

        # Delete user from database
        success = self.service.delete_profile(command.user_id)

        # If deletion succeeded, publish UserDeleted event
        if success:
            self._publish_user_deleted_event(
                user_profile,
                command.user_id
            )

        return success

    def _publish_user_deleted_event(self, user_profile, deleted_by_user_id):
        """Publish UserDeleted event to event store and RabbitMQ."""
        publisher = EventPublisher(self.db_session)

        event_data = {
            "user_id": user_profile['user_id'],
            "username": user_profile['username'],
            "email": user_profile['email'],
            "role": user_profile['role'],
            "deleted_at": user_profile.get('updated_at'),
            "deleted_by": deleted_by_user_id
        }

        publisher.publish_event(
            event_type="UserDeleted",
            aggregate_id=user_profile['user_id'],
            aggregate_type="UserProfile",
            event_data=event_data,
            user_id=deleted_by_user_id
        )

Auth-Service Event Consumer

The auth-service runs an event consumer that subscribes to user.deleted events and deletes users from Keycloak when they are deleted from the user-service.

File: backend/auth-service/event_consumer.py

class EventConsumer:
    """Consumes UserDeleted events and deletes users from Keycloak."""

    def __init__(self, keycloak_admin):
        self.admin = keycloak_admin
        self.rabbitmq_host = os.getenv('RABBITMQ_HOST', 'rabbitmq')
        self.rabbitmq_port = int(os.getenv('RABBITMQ_PORT', '5672'))

    def setup_queue(self):
        """Set up queue for UserDeleted events."""

        # Declare exchange (same as other services)
        exchange_name = 'talentlink.events'
        self.channel.exchange_declare(
            exchange=exchange_name,
            exchange_type='topic',
            durable=True
        )

        # Declare queue for auth service
        queue_name = 'auth.user.deleted'
        self.channel.queue_declare(
            queue=queue_name,
            durable=True
        )

        # Bind queue to exchange with routing key
        routing_key = 'user.deleted'
        self.channel.queue_bind(
            exchange=exchange_name,
            queue=queue_name,
            routing_key=routing_key
        )

        return queue_name

    def process_user_deleted(self, event):
        """Process UserDeleted event by deleting user from Keycloak."""

        event_data = event.get('event_data', {})
        user_id = event_data.get('user_id')
        username = event_data.get('username')

        if not user_id:
            print("⚠️ No user_id in event data. Skipping.")
            return

        try:
            # Delete user from Keycloak
            self.admin.delete_user(user_id=user_id)
            print(f"✅ User '{username}' (ID: {user_id}) deleted from Keycloak!")

        except Exception as e:
            # Handle 404 - user already deleted
            if "404" in str(e):
                print(f"⚠️ User not found in Keycloak. Already deleted.")
            else:
                print(f"❌ Failed to delete user: {e}")
                raise

9. Benefits & Trade-offs

Benefits of This Architecture

✅ Loose Coupling

Services communicate through events without direct dependencies. Job-service doesn't know about notification-service.

✅ Scalability

Can add multiple notification-service replicas to handle high email volume without affecting job-service.

✅ Resilience

If notification-service is down, events are queued in RabbitMQ and processed when it recovers. No data loss.

✅ Fast API Response

Employer gets immediate response after accepting application. Email sending doesn't block the request.

✅ Extensibility

Easy to add new event subscribers (SMS service, analytics, search indexer) without touching existing code.

✅ Audit Trail

Complete history of all ApplicationAccepted events stored in event store for compliance and debugging.

✅ Event Replay

Can rebuild system state or reprocess events by replaying from event store.

✅ Testability

Can test event publishing and consuming independently. Mock RabbitMQ for unit tests.

Trade-offs and Challenges

Challenge Impact Mitigation
Eventual Consistency Email may arrive a few seconds after acceptance Acceptable for notifications; user sees immediate success message
Added Complexity More moving parts (RabbitMQ, event store, consumers) Well worth it for scalability and resilience; good documentation helps
Debugging Difficulty Harder to trace event flow across services Use correlation IDs, structured logging, and distributed tracing (Jaeger)
Message Ordering Events may not always process in order Design events to be idempotent; use version numbers in event store
Infrastructure Cost Need to deploy and manage RabbitMQ RabbitMQ is lightweight and battle-tested; can use managed services in production

When to Use Event-Driven vs Synchronous

Rule of Thumb:
  • Use synchronous REST for user-facing operations requiring immediate data (login, browsing, fetching)
  • Use asynchronous events for side-effects, background tasks, and cross-service workflows
  • Use event sourcing when you need complete audit trail or ability to replay events
