1. Introduction to CQRS

CQRS (Command Query Responsibility Segregation) is a design pattern that separates read and write operations for a data store. Instead of using a single model for both reading and writing data, CQRS uses different models: Commands for writes and Queries for reads.

Core Principle

Commands: Change the state of the system (Create, Update, Delete)
Queries: Return data without modifying state (Read operations)

Commands (Write)

  • Modify system state
  • Perform validation
  • Execute business logic
  • Return success/failure

Queries (Read)

  • Never modify state
  • Return data
  • Can be cached
  • Optimized for reading

2. CQRS in User Service

The User Service implements CQRS to manage user profile operations. The implementation follows a clean, simple architecture that separates concerns and makes the codebase more maintainable.

3. Folder Structure

The CQRS implementation is organized in a clean, modular structure within the backend/user-service/cqrs/ directory:

backend/user-service/cqrs/ ├── __init__.py # Main exports for CQRS module ├── commands/ │ ├── __init__.py # Command exports │ └── user_commands.py # Command definitions ├── queries/ │ ├── __init__.py # Query exports │ └── user_queries.py # Query definitions └── handlers/ ├── __init__.py # Handler exports ├── command_handlers.py # Command execution logic └── query_handlers.py # Query execution logic
Important: Each module follows a clear separation of concerns. Commands and Queries are pure data structures (dataclasses), while Handlers contain the execution logic.

4. Commands - Write Operations

File: cqrs/commands/user_commands.py

Responsibility

  • Define data structures for write operations
  • Represent user intentions to modify state
  • Encapsulate all required parameters for operations
  • Provide type safety through dataclasses

Command Definitions

from dataclasses import dataclass
from typing import Optional


"""
User-related command definitions.
Commands represent write operations that modify state.
"""

@dataclass
class CreateUserProfileCommand:
    """Command to create a new user profile."""
    user_id: str
    username: str
    email: str
    role: str
    description: Optional[str] = None
    phone_number: Optional[str] = None
    secondary_email: Optional[str] = None
    address: Optional[str] = None


@dataclass
class UpdateUserProfileCommand:
    """Command to update an existing user profile."""
    user_id: str
    username: Optional[str] = None
    email: Optional[str] = None
    description: Optional[str] = None
    phone_number: Optional[str] = None
    secondary_email: Optional[str] = None
    address: Optional[str] = None


@dataclass
class DeleteUserProfileCommand:
    """Command to delete a user profile."""
    user_id: str


@dataclass
class UploadProfilePictureCommand:
    """Command to upload a profile picture."""
    user_id: str
    image_base64: str

Key Points

  • Immutable: Dataclasses are frozen data structures
  • Type-Safe: Python type hints ensure correct usage
  • Self-Documenting: Command names clearly indicate intent
  • Validation-Ready: Can add validation in __post_init__ if needed

6. Handlers - Execution Layer

File: cqrs/handlers/command_handlers.py

Responsibility

  • Execute commands by delegating to service layer
  • Transform command objects into service method calls
  • Handle command-specific business logic coordination
  • Return results or raise exceptions
from typing import Optional
from services import UserProfileService
from models import UserProfile
from cqrs.commands import (
    CreateUserProfileCommand,
    UpdateUserProfileCommand,
    DeleteUserProfileCommand,
    UploadProfilePictureCommand
)


class UserCommandHandler:
    """Handler for user-related commands."""

    def __init__(self, service: UserProfileService):
        self.service = service

    def handle_create_profile(self, command: CreateUserProfileCommand) -> UserProfile:
        """Handle CreateUserProfileCommand."""
        return self.service.create_profile(
            user_id=command.user_id,
            username=command.username,
            email=command.email,
            role=command.role,
            description=command.description,
            phone_number=command.phone_number,
            secondary_email=command.secondary_email,
            address=command.address
        )

    def handle_update_profile(self, command: UpdateUserProfileCommand) -> Optional[UserProfile]:
        """Handle UpdateUserProfileCommand."""
        updates = {}
        if command.username is not None:
            updates['username'] = command.username
        if command.email is not None:
            updates['email'] = command.email
        # ... more fields ...

        return self.service.update_profile(command.user_id, updates)

    def handle_delete_profile(self, command: DeleteUserProfileCommand) -> bool:
        """Handle DeleteUserProfileCommand."""
        return self.service.delete_profile(command.user_id)

    def handle_upload_profile_picture(self, command: UploadProfilePictureCommand) -> str:
        """Handle UploadProfilePictureCommand."""
        return self.service.upload_profile_picture(
            command.user_id,
            command.image_base64
        )

File: cqrs/handlers/query_handlers.py

Responsibility

  • Execute queries by delegating to service/repository layer
  • Transform query objects into service method calls
  • Optimize query execution (caching, pagination, etc.)
  • Return read-only data
from typing import List, Optional
from services import UserProfileService
from models import UserProfile
from cqrs.queries import (
    GetUserProfileByIdQuery,
    GetUserProfileByUsernameQuery,
    GetAllUserProfilesQuery
)


class UserQueryHandler:
    """Handler for user-related queries."""

    def __init__(self, service: UserProfileService):
        self.service = service

    def handle_get_profile_by_id(self, query: GetUserProfileByIdQuery) -> Optional[UserProfile]:
        """Handle GetUserProfileByIdQuery."""
        return self.service.get_profile(query.user_id)

    def handle_get_profile_by_username(self, query: GetUserProfileByUsernameQuery) -> Optional[UserProfile]:
        """Handle GetUserProfileByUsernameQuery."""
        return self.service.repository.get_by_username(query.username)

    def handle_get_all_profiles(self, query: GetAllUserProfilesQuery) -> List[UserProfile]:
        """Handle GetAllUserProfilesQuery."""
        return self.service.repository.get_all()

7. Integration with Routes

The routes layer integrates CQRS by creating command/query objects from HTTP requests and executing them through handlers.

Factory Function

Responsibility of get_handlers()

  • Create database session
  • Instantiate repository with session
  • Instantiate service with repository
  • Create command and query handlers with service
  • Return handlers and session for cleanup
def get_handlers():
    """Factory function for user CQRS handlers."""
    db = create_db_session()
    repository = UserProfileRepository(db)
    service = UserProfileService(repository)
    command_handler = UserCommandHandler(service)
    query_handler = UserQueryHandler(service)
    return command_handler, query_handler, db

Example: Create Profile (Command)

@user_bp.route("/profile", methods=["POST"])
def create_profile():
    """Create a new user profile - COMMAND."""
    data = request.get_json()

    # Step 1: Create command object from request data
    command = CreateUserProfileCommand(
        user_id=data["user_id"],
        username=data["username"],
        email=data["email"],
        role=data["role"]
    )

    # Step 2: Get handlers
    command_handler, _, db = get_handlers()

    try:
        # Step 3: Execute command
        profile = command_handler.handle_create_profile(command)
        return jsonify(profile), 201
    finally:
        db.close()

Example: Get Profile (Query)

@user_bp.route("/profile/<user_id>", methods=["GET"])
def get_profile(user_id):
    """Get user profile by ID - QUERY."""

    # Step 1: Create query object
    query = GetUserProfileByIdQuery(user_id=user_id)

    # Step 2: Get handlers
    _, query_handler, db = get_handlers()

    try:
        # Step 3: Execute query
        profile = query_handler.handle_get_profile_by_id(query)

        if not profile:
            return jsonify({"error": "Profile not found"}), 404

        return jsonify(profile), 200
    finally:
        db.close()

9. Component Relationships

Dependency Flow

Route Layer (routes.py)
    ↓ uses
Command/Query Objects (commands/*.py, queries/*.py)
    ↓ passed to
Handlers (handlers/*.py)
    ↓ delegates to
Service Layer (services.py)
    ↓ uses
Repository Layer (repositories.py)
    ↓ accesses
Database (via SQLAlchemy)

Component Interaction Table

Component Creates/Uses Depends On Returns To
Routes Command/Query objects Handlers, Factory HTTP Client
Factory Handlers, Service, Repository Database Session Routes
Command Handler Service calls Service Layer Routes
Query Handler Service/Repository calls Service/Repository Routes
Service Business logic Repository Handlers
Repository Database queries Database Session Service/Query Handler

How Components Complete Each Other

Commands + Command Handlers

Commands define what to do (the intention), while Command Handlers define how to do it (the execution). They are two halves of the same operation.

Queries + Query Handlers

Queries define what data to retrieve (the request), while Query Handlers define how to retrieve it (the data access). They work together to provide read operations.

Handlers + Service Layer

Handlers orchestrate the flow and validation, while the Service Layer contains the business logic. Handlers are the bridge between the API and business logic.

Service + Repository

Service contains business rules and validation, while Repository handles data persistence. Together they provide a complete data access pattern.

10. Benefits and Best Practices

Benefits of CQRS Implementation

1. Separation of Concerns

Read and write operations are completely separated, making the code easier to understand and maintain.

2. Scalability

Read and write operations can be scaled independently. Read-heavy workloads can use caching, while writes maintain consistency.

3. Clarity and Intent

Command and query names clearly express user intentions (CreateUserProfileCommand vs GetUserProfileByIdQuery).

4. Testability

Each component can be tested independently. Commands, Queries, and Handlers are easy to unit test.

5. Maintainability

Changes to read logic don't affect write logic and vice versa. Each operation is isolated.

6. Type Safety

Using dataclasses provides compile-time type checking and reduces runtime errors.

Best Practices

DO's

  • Keep commands and queries as simple data structures
  • Put business logic in the service layer, not handlers
  • Use descriptive names that express intent
  • Always close database sessions in finally blocks
  • Keep handlers focused on orchestration, not logic
  • Use type hints for better code documentation

DON'Ts

  • ✗ Don't put business logic in command/query classes
  • ✗ Don't mix reads and writes in the same handler method
  • ✗ Don't bypass handlers and call services directly from routes
  • ✗ Don't forget to handle exceptions properly
  • ✗ Don't create overly complex command/query hierarchies

Future Enhancements

Potential Improvements

  • Event Sourcing: Add event logging for all commands
  • Caching: Implement query result caching for better performance
  • Validation: Add command validators before execution
  • Async Operations: Support asynchronous command/query execution
  • Audit Trail: Track who executed which commands when
  • Middleware: Add pre/post execution hooks
